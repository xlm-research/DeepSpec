# Feature Specification: 统一 Ray 拓扑与生命周期，扩展多节点 draft 训练

**Feature Branch**: 沿用当前工作分支；未配置分支 hook，本次不创建或切换分支。

**Feature Directory**: `specs/001-unify-ray-topology`

**Created**: 2026-09-20

**Status**: Draft

**Input**: User description: "基于刚完成的 TorchSpec 对比评估，为方案 B 生成规格：统一 Ray 拓扑与生命周期，扩展多节点 draft 训练，保留原生 vLLM Ray、TorchTitan 和字节预算契约。"

本功能服务于训练任务维护者：使用一致的资源声明、运行状态和失败规则管理现有单机/两机任务。用户在澄清中将本轮主验收布局 M2 指定为两个推理节点、一个 draft 训练节点；每个推理模型副本跨两个推理节点共同计算，增加推理卡数时增大 DP 副本数。三台节点各分配 8 张 GPU，共 24 张；推理为 TP8×DP2，每个副本在两个推理节点各使用 4 GPU，第三台训练节点采用 TP4×DP2。首版同时交付 M3 跨节点 draft 训练：一个推理节点使用 4 GPU 运行 TP4×DP1，两个训练节点各使用 4 GPU，共同完成 TP4×DP2 训练；该 12 GPU 布局单独验收，不替代 M2。用户要求保留现有推理后端、训练语义与特征内存契约；本规格规定结果和约束，不决定具体类、接口或文件拆分。

依据：[方案 B](../../.specify/assessments/torchspec-ray-management/concept.md)、[评估决策](../../.specify/assessments/torchspec-ray-management/decision.md)、[源码比较与建议](../../.specify/assessments/torchspec-ray-management/comparison.md)。

## Clarifications

### Session 2026-09-20

- Q: 首版新增的多节点 draft 训练，你希望采用哪种资源布局验收？ → A: 2 节点推理，1 节点训练。此回答确认节点角色分配，未确认每节点 GPU 数或推理并行方式。
- Q: 两个推理节点是各自运行模型副本，还是共同承载一个跨节点模型？ → A: B，卡数多了就增大 dp。每个推理副本的模型分片跨两个节点共同计算；推理资源增加时，通过增加相同模型并行规模的 DP 副本扩展，而不是把新增卡继续并入同一个副本。

- Q: 每个跨节点推理副本，你希望固定使用多大的 TP（张量并行）规模？ → A: tp 设置为 8。该回答针对推理：每副本 TP8，两个推理节点各占 4 张 GPU；更多推理 GPU 用于增加 DP，不自动改变 draft 的训练 TP。

- Q: 两个推理节点和一个训练节点，本次分别使用多少张 GPU？ → A: A。三节点各使用 8 张 GPU，共 24 张：推理 TP8×DP2，每个副本在两推理节点各占 4 GPU；单节点 draft 训练 TP4×DP2。

- Q: 首版是否还需要支持 draft 跨两个训练节点运行？ → A: B。首版同时支持跨节点 draft 训练，另以原草案“1 推理节点＋2 训练节点、训练 TP4×DP2”独立验收，记为 M3：推理节点 4 GPU、TP4×DP1；两个训练节点各 4 GPU，每节点一个 TP4 组，通过跨节点 DP2 协同训练。M2 的 24 GPU、推理 TP8×DP2 主布局保持不变。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 启动前看清资源布局和支持范围 (Priority: P1)

作为训练任务维护者，我希望从同一份任务声明看清推理、训练及特征存储的位置、卡数和训练分组，并在加载模型前知道配置是否可用，以免占用部分 GPU 后才发现布局错误。

**Why this priority**: 声明与实际分配一致，是多节点扩展和故障清理的共同前提。

**Independent Test**: 仅运行准备/预览操作，使用合法、资源不足、节点重复和不支持的布局，检查生成的计划和拒绝原因；不需要加载模型。

**Acceptance Scenarios**:

1. **Given** 首版支持矩阵内的一种配置，**When** 用户预览任务，**Then** 得到包含运行标识、角色、节点选择、每节点 GPU/CPU 数、训练分组、特征存储位置及逐节点预算的完整计划，且不创建模型进程、不预留 GPU、不分配大型特征池。
2. **Given** 存在 GPU 集合重叠、节点缺失、分组不能整除或不支持的组合，**When** 用户启动任务，**Then** 在 GPU 预留或模型加载前拒绝，并指出冲突字段与原因。
3. **Given** 预览时资源充足但启动时资源已被其他任务占用，**When** 任务不能在资源等待期限内完成分配，**Then** 明确失败、释放本次部分分配，并保留其他任务。

### User Story 2 - 使用已有配置继续训练 (Priority: P1)

作为当前项目使用者，我希望已有单机与两机训练配置继续可用，并获得一致的运行状态、输出和错误解释，从而可以逐步迁移管理方式而不改变训练内容。

**Why this priority**: 已完成的 4K/128K 调试结果是回归基线，管理层改造必须保留其价值。

**Independent Test**: 分别用已有配置和新声明执行同一现有布局，对照资源分配、输入计划、更新数、特征校验和最终保存状态。

**Acceptance Scenarios**:

1. **Given** 现有受支持单机或两机配置，**When** 用户使用保留的启动方式运行，**Then** 配置被解释为同等任务，模型、样本顺序、训练分组、每次更新样本数和字节预算不被静默修改。
2. **Given** 相同输入、初始训练状态与并行配置，**When** 任务成功结束，**Then** 已消费样本及微批顺序与计划一致，读取校验通过，更新数与可独立加载的最终 checkpoint 相符。
3. **Given** 旧配置与新声明存在相互冲突的值，**When** 解析配置，**Then** 明确拒绝冲突；不能静默选择一个会改变训练结果的值。

### User Story 3 - 验证跨节点推理与跨节点 draft 训练 (Priority: P1)

作为训练任务使用者，我希望在 M2 中让每个目标模型推理副本跨两个推理节点完成计算；有更多推理 GPU 时增加这种跨节点副本的 DP 数量，分担不同样本，并为一个独立的 draft 训练节点提供特征。我也需要在 M3 中由一个推理节点提供特征，让两个训练节点共同完成同一 draft 训练任务。各角色只使用分配给自己的设备和样本，两种布局分别验证。

**Why this priority**: 用户确认首版同时包含跨节点推理和跨节点 draft 训练；单个布局通过不能证明另一种能力已完成。

**Independent Test**: 分别运行 M2（两个推理节点、一个训练节点）和 M3（一个推理节点、两个训练节点），完成真实特征生产、跨节点传输、draft 训练、最终保存和退出；检查每个节点的参与证据，以及训练身份、样本归属与更新记录。

**Acceptance Scenarios**:

1. **Given** M2 布局及充足资源，**When** 启动训练，**Then** 两个 TP8 推理副本各自在两个推理节点使用 4 张 GPU，每个请求由其所属副本在两个节点协作完成；第三个节点的 8 张 GPU 组成 draft TP4×DP2，全部实际设备与各角色计划一致。
2. **Given** 推理结果以不同于输入计划的顺序就绪，**When** 训练节点消费特征，**Then** 仍按持久化计划确定样本与训练组的对应关系，不按推理完成顺序重新分配样本。
3. **Given** 全局每次更新 4 个样本、共 12 个样本，**When** 完成训练，**Then** 所有训练参与者完成 3 次一致的更新，最终保存包含匹配的更新数与下一全局微批位置。
4. **Given** 任一推理节点或训练节点无法加入或中途失联，**When** 达到相应等待期限或检测到致命错误，**Then** 全任务失败，不允许缺少计划内角色的任务报告完整成功。
5. **Given** 两个推理节点的分配额度从各 4 GPU 增加到各 8 GPU，**When** 分别以 DP1 和 DP2 的配置启动，**Then** 推理 TP 均保持为 8，每个副本在两节点各占 4 GPU；两个 DP 副本按输入计划承担不同样本，训练 TP4×DP2、更新边界与全局每次更新样本数不变。
6. **Given** M3 的三个独立节点各分配 4 GPU，**When** 启动训练，**Then** 推理节点运行 TP4×DP1，两个训练节点各承载一个 TP4 模型组，通过跨节点 DP2 协同更新同一 draft 模型；8 个训练参与者的全局身份唯一，节点、本地身份、训练组与指定读者映射一致。
7. **Given** M3 的任一训练节点失联或任一训练参与者发生致命错误，**When** 检测到故障或到达等待期限，**Then** 两个训练节点及生产侧共同停止，整个任务失败，并遵守逐节点预算、特征释放和有界清理契约；剩余训练节点不能独立继续或报告成功。

### User Story 4 - 长序列下保持可解释的内存上限 (Priority: P1)

作为运行 128K 训练的使用者，我希望推理、传输、预取和训练读取受到同一套容量规则约束，即使某个读者慢或删除失败，也不会提前回收额度或删除仍被使用的源特征。

**Why this priority**: 扩展节点不能削弱现有字节预算，否则配置上的扩展会转化为长序列内存故障。

**Independent Test**: 用已知字节数的变长特征和可控制的读者速度验证准入、写入、读取确认及删除；再在真实 128K 场景核对峰值和最终释放。

**Acceptance Scenarios**:

1. **Given** 下一样本超过剩余额度或任一相关节点不足以承担新的更新组，**When** 请求生产，**Then** 暂停新准入或在规定期限内失败，不能绕过预算、静默丢弃样本或用未声明的存储淘汰代替背压。
2. **Given** 同一个样本有多个指定读者，**When** 只有部分读者完成读取，**Then** 源对象保留，且该样本的预留额度不退还；其他训练组不能领取该样本。
3. **Given** 所有指定读者已完成读取但删除失败，**When** 发生重试或最终失败，**Then** 删除确认前不得退还容量，重试耗尽时任务失败并记录样本和原因。
4. **Given** 容量不足以完成一个完整更新组，**When** 校验计划，**Then** 在加载模型前拒绝；运行中已经准入的更新组仍须满足启动时证明的暂存上限，避免因等待其后续样本而无法推进。

### User Story 5 - 失败或取消时只清理本次任务 (Priority: P1)

作为共享集群维护者，我希望初始化失败、训练失败、超时和主动取消都能得到明确终态，并在有限时间内释放本次任务拥有的资源，保护其他任务与已有服务。

**Why this priority**: 多节点运行需要可控的失败边界，不能依赖进程最终自行退出。

**Independent Test**: 在资源申请、模型初始化、特征写入、训练读取与退出各阶段注入故障或取消，核对终态、耗时、残留资源和旁路任务状态。

**Acceptance Scenarios**:

1. **Given** 部分角色已经启动而另一角色初始化失败，**When** 启动流程终止，**Then** 整体进入失败终态，并在清理期限内释放已经创建的本次资源。
2. **Given** producer、任一训练参与者或存储服务发生致命错误，**When** 系统检测到错误，**Then** 停止继续准入新特征，通知等待方并终止整个任务，不能略过失败样本后报告成功。
3. **Given** 用户主动取消，**When** 取消流程结束，**Then** 状态为 cancelled，能够与运行错误区分，且遵守相同的资源清理规则。
4. **Given** 同一任务重复收到清理请求，且集群存在无关任务/用户启动的服务，**When** 清理执行，**Then** 不误杀、不重复释放别人的资源、不关闭共享集群。
5. **Given** 某节点已失联而无法核实远端进程，**When** 清理期限到达，**Then** 返回失败或取消终态，同时列出未确认回收的节点与资源；不得宣称全部清理成功。

### User Story 6 - 从一份状态记录判断任务是否健康 (Priority: P2)

作为调试者，我希望看到声明与实际资源、各角色进度、当前等待原因、内存水位和最终保存位置，以便区分推理、传输或训练导致的等待。

**Why this priority**: 可观测结果有助于调试和后续优化，但本次不承诺吞吐提升。

**Independent Test**: 对正常运行、容量阻塞与故障运行读取状态和事件记录，核对其是否与进程、内存及保存结果一致。

**Acceptance Scenarios**:

1. **Given** 一个正在运行的任务，**When** 用户查看状态，**Then** 获得实际角色落点、生产/读取/更新进度、当前等待原因、每节点内存预算与观测值。
2. **Given** 一个正常结束的任务，**When** 用户查看结果，**Then** 成功状态同时对应所有计划样本处理完成、特征释放、最终保存校验通过和本次运行资源回收确认。
3. **Given** 一个失败任务，**When** 用户查看结果，**Then** 能定位失败阶段、相关角色/节点/样本、首个已知原因及清理结果，不把“样本已读完”展示为“训练已提交”。

### Edge Cases

- 节点标签或地址匹配到零个/多个节点、节点重复、推理和训练设备重叠：按确定的计划唯一性规则拒绝。
- GPU 空闲位置不连续、总空闲卡数充足但单个训练组不能放置：必须核对实际设备集合与分组约束，不能以连续编号或总数代替验证。
- 原生推理后端自行保留资源：同一组物理资源不能被外层再次预留，导致自己等待自己。
- 推理卡数增加但不能组成完整的跨两节点副本，或其中一个节点不足以承载声明的副本分片：不得仅按集群 GPU 总数增大 DP，不得自动扩大已有副本的模型并行规模；对无法满足的声明明确拒绝。
- M3 的训练全局身份重复、本地身份与设备不符、TP 组跨错节点或 DP/指定读者映射不一致：必须在训练消费前拒绝；一个训练节点就绪不能代表整个训练组就绪。
- 计划预览后资源变化、部分角色先取得资源：有界等待并回滚本次部分分配。
- 节点 Python/依赖/源码、模型或输入计划不一致：加载模型前尽可能验证；无法完成所需一致性检查则不得进入训练。
- 单样本、完整更新组或任一节点的副本/暂存量超过预算：拒绝运行，并指出是哪一项超限。
- 结果乱序、重复写入/发布/领取/确认、错误读者、特征身份/尺寸/校验值不符：拒绝无效操作；影响数据一致性的错误使任务失败。
- 所有读者已读完、但训练更新尚未完成：允许按现有契约删除源对象，不能因此推进已提交训练进度；本版本不承诺故障后重放。
- 节点失联、通信超时、删除重试耗尽、checkpoint 不完整：有限失败并保留诊断证据，不默认为可恢复状态。
- driver 意外退出：可达节点上的本次角色和子进程应在声明的监督/清理期限内停止；不可达资源的回收状态需在重新连接后的核查中确认。
- 测试资源不足或节点不可达：可记录为验收阻塞，不能以模拟测试结果替代多节点真实训练已通过。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为每次运行建立唯一运行标识，并关联不可变的输入计划、训练目标身份、角色拓扑、资源预算和最终结果；资源与样本不能跨运行混用。
- **FR-002**: 用户 MUST 能用统一的任务声明表达首版支持矩阵中的布局，并获得不启动模型、不预留 GPU、不分配大型特征池的准备/预览结果。
- **FR-003**: 系统 MUST 在启动前校验节点选择、资源数量、角色隔离、训练组整除关系、样本更新组、超时配置与支持矩阵；对不支持的组合明确拒绝。
- **FR-004**: 旧版受支持配置和启动方式 MUST 保持可用；向统一声明转换时不得静默改变训练语义、预算或设备归属，冲突配置必须报错。
- **FR-005**: 系统 MUST 在角色开始 GPU 工作前验证实际节点/设备集合与资源计划一致；同一物理 GPU 在本版本不得同时属于推理和训练角色，也不得重复预留。
- **FR-006**: 每次运行 MUST 明确区分自建资源和外部已有资源，并记录其创建/回收责任；任务退出只能回收本次拥有的资源。
- **FR-007**: 系统 MUST 使用一致的生命周期状态：preparing → allocating → initializing → ready → running → draining → succeeded；活动状态遇致命错误或超时进入 failed，用户主动取消进入 cancelled。ready 仅表示所有必需角色、通信和存储已满足启动条件；训练不得提前消费未就绪角色的数据。
- **FR-008**: 资源申请、初始化、就绪等待、运行、传输/读取等待和清理 MUST 有可查看的正数有限期限；预期背压在期限内属于等待，超过期限必须转为明确失败。配置缺失时可使用已记录的有限默认值，不能无限等待。
- **FR-009**: 系统 MUST 支持 M2 的 8/8/8 GPU 分配：两个推理节点共同运行 TP8×DP2，每个模型副本跨两个节点且各占 4 GPU；第三个独立节点以 8 GPU 运行 draft TP4×DP2。增加推理资源时扩展同规模 DP 副本而保持 TP8 不变。各节点仅使用分配给自己的设备，参与者身份、模型分片、DP 副本归属及训练分组必须与确认的计划一致。
- **FR-010**: 训练 MUST 保持持久化输入计划规定的顺序、样本归属与更新边界；推理完成顺序不能改变样本集合、训练组分配或全局每次更新的样本数。
- **FR-011**: 系统 MUST 在写入前按实际预期字节数和样本窗口预留特征容量，并校验实际发布的字节数、特征身份、shape、dtype 与计划一致；未预留或未写完的特征不得作为可读数据发布。
- **FR-012**: 容量校验 MUST 覆盖完整更新组及各相关节点的特征池、生产暂存、在途传输、读取/校验和预取副本；启动时检查配置上限，运行中在新的更新组准入前检查节点余量。
- **FR-013**: 每个样本 MUST 只有计划指定的读者能够读取；只有全部指定读者已完成并持有独立有效副本后，才允许删除源对象。只有删除确认成功后才退还容量。
- **FR-014**: 系统 MUST 将读完确认与训练提交作为不同事件记录；后续反向计算所需的训练侧副本须保持有效，源对象删除不能冒充 optimizer update 或 checkpoint 已完成。
- **FR-015**: 系统 MUST 对致命推理、训练、传输、存储和一致性错误执行全任务失败处理，终止新的准入并唤醒/终止等待方；不得静默跳过失败样本、让部分训练节点独立继续或自动改变任务规模。
- **FR-016**: 退出清理 MUST 覆盖部分启动与完整启动、正常结束、失败、取消和 driver 意外退出；清理须可重复执行，并分别报告已确认回收与未确认回收的资源。
- **FR-017**: 成功结果 MUST 在独立核查最终完整 checkpoint 后产生，核查更新数、计划身份与下一全局微批位置，并与运行中已消费样本对应；全部源特征已释放且本次运行资源回收确认之前不得报告完整成功。
- **FR-018**: 系统 MUST 保存实际角色落点、各节点环境一致性检查、样本生产/读取进度、已完成更新、容量与峰值、等待原因、特征生产速度、传输/训练耗时、最终 checkpoint 和失败/清理结果；读完与已提交进度须分别可见。
- **FR-019**: 系统 MUST 保留原生 vLLM Ray 推理后端和 TorchTitan 训练路径，包括现有 DSpark 特征契约、loss/掩码/归一化定义、梯度累积、优化器与完整 checkpoint 语义；本功能不得通过切换上游 trainer、执行后端或数学定义实现管理层兼容。
- **FR-020**: 同一首版布局的所有参与节点 MUST 使用兼容且可核验的环境、源码、模型和数据身份；沿用现有 TCP/CPU 特征传输路径作为必验基线，新增 RDMA 或 GPU 直收优化不属于本功能交付条件。
- **FR-021**: 系统 MUST 支持并独立验收 M3：一个推理节点使用 4 GPU 运行 TP4×DP1，两个独立训练节点各使用 4 GPU，每节点保留一个完整 TP4 模型组，以跨节点 DP2 完成同一 draft 训练任务。8 个训练参与者的全局/本地身份、设备、TP/DP 分组及指定读者映射必须与计划一致；两个训练节点须共同就绪、遵守相同的全局更新边界并产出可独立核查的完整 checkpoint。所有节点均受 FR-011–016 的预算、确认、失败和清理契约约束；任一训练参与者致命失败必须终止整个任务。

### Scope & Compatibility Constraints

TP 指一个模型计算组使用的卡数；DP 指处理不同样本的数据并行组数。训练“参与者”指持有一个分布式训练身份的进程；这些是训练领域概念，不规定 Ray actor 的实现粒度。

| 标识 | 首版必须支持的布局 | 推理资源 | draft 训练资源 | 资源关系 |
|---|---|---|---|---|
| M0 | 现有单机布局 | DP1 × TP4，共 4 GPU | DP1 × TP4，共 4 GPU | 同一节点共 8 GPU，推理/训练设备互不重叠 |
| M1 | 现有两机角色分离布局 | 一个推理节点，DP1 或 DP2，每组 TP4 | 一个训练节点，DP1 或 DP2，每组 TP4 | 两个不同节点；每个角色按 DP 使用 4 或 8 GPU，保留既有组合 |
| M2 | 新增双推理节点、单训练节点主布局 | 两个节点各 8 GPU，合计 TP8×DP2；每副本在两个节点各占 4 GPU | 第三个节点 8 GPU，TP4×DP2 | 三个不同节点，共 24 GPU；每个推理副本跨两节点，训练独占第三节点 |
| M3 | 新增单推理节点、双训练节点独立验收布局 | 一个节点 4 GPU，TP4×DP1 | 两个节点各 4 GPU，合计 TP4×DP2；每节点一个完整 TP4 模型组 | 三个不同节点，共 12 GPU；训练 DP 跨两节点，推理独占另一节点 |

- M2 已确认两个推理节点各 8 GPU、训练节点 8 GPU：推理 TP8×DP2，训练 TP4×DP2。每个推理副本跨两个节点且各占 4 GPU；两个节点各自运行完整副本不满足要求。DP 扩展对照使用推理各 4 GPU 时的 TP8×DP1，训练仍为 TP4×DP2；减少额度后未分配的推理 GPU 不得被该任务使用。
- 在 M2 跨节点推理布局中，对分配给两个推理节点的 GPU 数 G1、G2，可容纳的 DP 上限为 min(floor(G1/4), floor(G2/4))；每个实际副本消耗两端各 4 GPU，共 8 GPU。更大的 DP 声明必须拒绝；不足一个完整副本的剩余卡不能扩大该副本的 TP。这里的 G1/G2 指本任务分配额度，不是整台机器未授权使用的全部卡数。
- 本次增加 DP 的规则用于按资源规模声明启动配置；不因此引入运行中自动扩缩容，也不把推理 DP 增大自动应用到 draft 的训练 DP 或全局 batch。
- 跨节点 draft 训练是首版必交付能力，以 M3 单独验收：每个训练 TP4 组留在一个节点内，两个模型组通过跨节点 DP2 协同训练。M2 与 M3 都必须通过，各自的结果不能替代另一布局的证据；首版不要求把跨节点推理与跨节点 draft 同时组合为四节点布局。
- M0/M1 保留当前 TP4、CP=PP=1 的 streaming 支持边界；M2 推理新增跨两节点的 TP8，draft 训练沿用单节点 TP4×DP2、CP=PP=1；M3 推理沿用单节点 TP4×DP1，draft 训练为跨两节点 TP4×DP2、CP=PP=1。推理 TP8 的确认针对 M2，不改变 M3 原草案的 TP4 推理基线。其他并行方式须独立声明并验证，不能仅凭参数存在推定支持。
- 首版保留现有全局每次更新 4 个样本的配置语义；按训练 DP 计算本地微批/累积关系，不能通过改变全局 batch 掩盖多节点错误。
- 不要求所有后端强制使用一个 placement group，也不要求改成每训练 rank 一个 Ray actor；这些属于技术方案阶段的选择，必须服从 FR-005/006/019。
- 已确认范围包含现有布局等价迁移、M2 双推理节点对单训练节点的管理、M3 跨两个训练节点的 draft 训练，以及所有布局的逐节点预算、失败清理和运行证据。自动重启/特征重放、在线改变 world-size、GPU 显存轮换、按结果完成顺序重排训练计划、RDMA 调优、新训练算法和新评估调度均不在首版范围。
- 保留现有 checkpoint 能力，但不引入新的无损流式恢复承诺，不将完整 checkpoint 与内存中特征状态混为一谈。

### Key Entities *(include if feature involves data)*

- **Run / 运行**：唯一身份，关联输入计划、角色拓扑、预算、生命周期、输出与失败/清理证据。
- **Topology Plan / 拓扑计划**：各角色的目标节点、资源数量、每个推理副本的模型分片与固定规模、推理 DP 数、训练分组及支持矩阵身份；与实际分配结果关联但不等同。
- **Inference Replica / 推理副本**：一个完整目标模型的分布式实例；M2 中每副本固定 TP8，横跨两个推理节点且各用 4 GPU，独立承担分配给该 DP 副本的样本。增加 DP 时复制同规模实例，模型身份与特征契约保持一致。
- **Allocation / 实际分配**：已获得的节点/设备/服务、对应角色、所属运行、所有者与回收状态；设备身份由节点与设备标识共同确定。
- **Training Participant / 训练参与者**：全局与本地身份、所在节点、设备及所属 TP/DP 训练组；共同参与同一个训练任务。M3 的两个 TP4 模型组分别位于两个训练节点，同一 TP 位置的参与者跨节点组成 DP 组并遵守共同的更新边界。
- **Sample Plan / 样本计划**：运行内不可变的样本身份、顺序、目标模型/特征身份、分组归属及更新边界。
- **Feature Record / 特征记录**：样本对应的字节数、内容校验、生产状态、指定读者、读完确认与源对象删除状态；用于准入和容量归还。
- **Node Budget / 节点预算**：该节点池、暂存、在途和副本需求及安全余量、运行期观测；释放池内额度不等于释放操作系统内存。
- **Training Commit / 训练提交**：完整 checkpoint、已提交更新数、计划身份及下一全局微批位置；区别于特征读完确认。
- **Run Evidence / 运行证据**：状态事件、实际落点、校验与性能观测、错误原因和清理报告；用于判断验收是否真正完成。

## Success Criteria *(mandatory)*

## Assumptions

- **A1 — 已确认的新增布局与扩展方式**：用户确认 M2 为两个推理节点与一个训练节点，各使用 8 GPU，共 24 GPU；推理 TP8×DP2，每副本在两节点各占 4 GPU，训练 TP4×DP2。新增推理卡数用于增加同规模 DP 副本。M2 是主验收布局；用户同时确认原草案的一个推理节点、两个训练节点布局作为 M3 纳入首版并独立验收。M3 为推理 TP4×DP1、两个训练节点各一个 TP4 组组成训练 DP2，共 12 GPU，不改变 M2 的 24 GPU 与推理 TP8 选择。
- **A2 — 环境与访问**：运行在用户现有可信训练环境中，相关节点拥有可核验的相同项目/依赖和可访问的模型、数据、输出路径。本功能不新增身份认证系统、集群调度基础设施或自动环境分发。
- **A3 — 存储基线**：首轮继续使用当前 TCP/CPU 特征池及完整读取校验；逐节点预算须随实际 pool 和读者位置变化。是否引入分池属于后续方案选择，不改变容量与 ACK 的验收规则。
- **A4 — 失败策略**：沿用 fail-fast；先保证有界失败、清理和证据，不增加自动恢复。具体各阶段期限须在运行配置中提供或明示有限默认值，不预设模型必须在某个未经测量的固定秒数内加载完成。
- **A5 — 性能范围**：首版目标是扩展能力、语义兼容与可诊断性，没有用户指定的吞吐提升比例或长期可用性 SLA。记录性能指标，但不把未经对照的性能收益作为通过依据。
- **A6 — 数值兼容**：保留已有数学定义和输入计划；跨节点浮点结果不要求无依据的逐 bit 相同。相同并行布局沿用已有数值回归准则；新布局至少满足样本/更新/校验和完整保存的共同验收条件。
- **A7 — 验收资源**：M2 需要真实的两个推理节点和一个独立训练节点，各可为本任务分配 8 GPU，共 24 GPU；M3 需要一个推理节点和两个独立训练节点，各分配 4 GPU，共 12 GPU。两种验收均须满足对应内存与网络条件，可以顺序复用同三台物理节点并调整角色与额度，不要求同时运行。用户确认的是目标资源布局，不等于已验证这些节点可连接或空闲；资源缺失时只标记验收阻塞，不能删去已确认的节点角色要求或宣称功能完成。
- **A8 — 工作流与范围**：本次仅生成规格、质量检查表与当前功能记录；不修改训练实现、不启动 GPU 任务、不提交或发布代码。之后的 plan 负责具体实现方法与任务拆分。
