## 已确认范围

- **长度**：输入与输出合计最多 `262144` tokens。输入包含最终送入模型的聊天模板等 token；不能输入 262144 后再额外生成。
- **负载**：先验收单条长请求的 prefill、多步生成，以及结束后的后续请求和状态复用。首阶段没有多条长请求同时驻留的并发承诺。
- **prefill**：启用分块 prefill，初始单步 token 预算为 8192；保留完整请求历史，各执行层继续使用自己的 KV/GDN 状态，prefix caching 关闭。
- **长请求验收**：必须完成 `262128 输入 + 16 输出` 与 `258048 输入 + 4096 输出` 两组用例，每组结束后均在同一引擎运行短请求检查状态复用。
- **继承的部署与验收边界**：继续使用原 checkpoint、单机八张 H800、TP=8、PP=1、DP=1、文本推理、BF16 主干、FP32 router/SSM、eager 和 V2 runner；沿用不做数值对照、不设吞吐或时延硬指标的决定。

## 分块与容量：源码证据及推导

现有 GDN 的 [metadata 构建](../vllm/vllm/v1/attention/backends/gdn_attn.py:390)根据已计算 token 数判断是否存在前段状态。[卷积路径](../vllm/vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py:1286)接收并更新卷积状态；[SSM 路径](../vllm/vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py:1430)读取执行层中该请求的初始状态，并在 chunk 结束时写回最终状态。设计阶段据此确认底层已有状态续接机制；实施后已验证 Loop 的完整分块运行及后续请求复用，证据范围限于功能与结构，不包含数值对照。

[混合模型配置](../vllm/vllm/model_executor/models/config.py:630)在关闭 prefix caching 时使用 `mamba_cache_mode=none`。分块 prefill 和前缀缓存是不同能力；不能为了前者自动开放后者。

按当前模型、TP=8 和 BF16 KV 作以下静态估算，单位为二进制 GiB/MiB：

| 单个 rank 的对象 | 一次处理 262144 tokens | 一次处理 8192 tokens |
| --- | --- | --- |
| 完整 256K 请求的 20 层 attention KV 有效数据 | 5 GiB | 仍为 5 GiB |
| 一份四流 BF16 残差 | 8 GiB | 256 MiB |
| 一份四流 FP32 router 展平/归一化张量 | 16 GiB | 512 MiB |

KV 估算为 `262144 × 20 × 2(K/V) × 1(KV head/rank) × 256(head dim) × 2(bytes)`。TP=8 大于 4 个 KV heads，每个原始 head 被复制到两个 rank；不能将全模型 KV 直接除以八。四流张量依据 `[tokens, 4, 4096]` 及 [router 的 FP32 转换](../vllm/vllm/model_executor/models/qwen3_5_loop.py:56)推导。

这些是指定对象的大小，不是总显存或实测峰值；KV 数字不含引擎缓存池的预分配、块填充与混合状态开销，激活数字不含其他同时存活的临时张量。分块可控制单次激活的长度维度，但不会把 256K 历史缩成 8K，也不会取消完整 attention 的长序列计算量。

当前 eager router 中，BF16 residual、FP32 flat 与 normalized 同时持有引用；一次处理 262144 tokens 时，仅这三项约为每卡 40 GiB，还不含其他张量。V2 的[启动 profiling](../vllm/vllm/v1/worker/gpu/model_runner.py:870)也使用 `max_num_batched_tokens` 作为 dummy forward 的规模。因此已选方案将上下文上限与单步 token 预算分开配置，初始单步预算为 8192。实际峰值与耗时由后续运行记录，不由这组估算推定。

## 交付方案（已确认并完成验收）

采用以下配置：

```text
max_model_len=262144
max_num_batched_tokens=8192
max_num_seqs=1
enable_chunked_prefill=true
enable_prefix_caching=false
```

其余精度、拓扑及运行模式沿用已确认基线。解除 Loop 专用的 8K 上限和分块禁用限制；非分块时的批次预算约束仍须保留。保留 checkpoint 的位置配置和 RoPE，不通过截断历史、共享执行层状态或降低缓存精度来满足长度目标。

复用现有标准服务和离线生成入口，更新共用配置、输入长度提示与说明文档，保留 8K 验证记录并另存 256K 的有效配置和运行结果。优先复用现有 GDN/attention 的状态续接；若发现接口缺口，记录具体失败证据再确定改动范围。

验收覆盖以下行为，初始单步预算 C 为 8192：

| 检查 | 用例与通过条件 |
| --- | --- |
| 既有能力 | 短文本和 8K 请求仍可完成 prefill、多步 decode 与正常结束，并保留已通过的 8K 非分块配置的回归检查 |
| 分块边界 | 输入长度取 `C-1`、`C`、`C+1`、`2C+2`，即 8191、8192、8193、16386，检查部分块与极短尾块能够续接，且每个执行层状态绑定正确 |
| 长度递增 | 在 32K、64K、128K 到 256K 的总长度上逐级验证并记录异常，以定位资源或长度相关限制 |
| 256K 边界 | 实际完成 262128 输入和 16 输出，压力用例忽略 EOS 以走满预算，保留所选 token 的有限 logprob 检查 |
| 持续解码 | 实际完成 258048 输入和 4096 输出，同样使用长度压力设置并检查所选 token 的有限 logprob；正常 EOS 停止用例单独记录 |
| 请求复用 | 上述每组长请求完成后，都在同一引擎再次完成短请求；检查状态槽使用及后续运行，无资源耗尽或遗留错误 |
| 长度与停止 | 超出上下文范围的输入被拒绝；剩余生成空间、EOS 及停止条件遵循既有引擎行为 |

运行记录需区分输入与输出实际 token 数、是否真正经历分块、完成状态和异常；记录可观测的 prefill/生成耗时及显存情况用于复现，不设额外性能门槛。不增加参考模型、整段对分块的数值对照或长文本质量评测。

两个主验收用例在单请求、8192 单步预算且无抢占时均预计经历 32 次 prefill：第一组最后一块为 8176 tokens，第二组最后一块为 4096 tokens。实际报告须从调度或 forward 的运行信息确认分块发生及已处理长度的推进，不能仅由配置推算后声称已测得。GDN 的卷积/SSM 状态和 attention KV 按执行层续接；有限 logprob 与运行完成属于功能证据，不替代数值对照。

实施顺序是先调整配置校验及共用入口，再检查 8K 回归和分块尾部边界，然后递增长度并完成两组 256K 用例及状态复用。已有通过检查在实现未再次变化且无新疑点时不重复运行；若实际失败，需要保留失败长度、分块进度、异常和显存证据，再修复对应接口。

## 实施与运行记录

实现仅调整 Loop 配置校验和共用示例：上下文上限为 262144，分块预算允许小于上下文长度，prefix caching 仍被拒绝；示例默认使用 8192 单步预算，输入长度错误在加载模型前被拒绝。现有模型前向、共享权重及 attention/GDN 状态续接代码无需改动。

配置回归 5 项通过，修改的 vLLM 文件通过相关 pre-commit hooks，示例通过 Ruff 检查。八卡 8K 非分块回归的短请求和 8176+16 均通过。256K 配置下完成 17 个生成用例，涵盖短请求、8191/8192/8193/16386 分块边界及 32K/64K/128K 总长度请求。

| 主验收 | 实际 prefill（八个 rank 均一致） | prefill 耗时 | decode 耗时 | 请求总耗时 | 后续短请求 |
| --- | --- | --- | --- | --- | --- |
| 262128 输入 + 16 输出 | 32 块，最后 8176 tokens | 40.17 秒 | 5.45 秒 | 45.64 秒 | 15+16，通过 |
| 258048 输入 + 4096 输出 | 32 块，最后 4096 tokens | 39.70 秒 | 1492.75 秒 | 1532.46 秒 | 15+16，通过 |

诊断 worker 记录实际 `SchedulerOutput` 后原样调用父类执行路径。各 rank 的 prefill 起点连续、单块不超过 8192、总和等于输入长度；长请求在后续短请求的快照中均收到完成通知。八个 rank 均注册 80 个执行层、20 个 attention 和 60 个 GDN 状态，attention/卷积状态为 BF16，SSM 为 FP32。所有生成用例所选 token 的 logprob 有限；这些检查不构成分块与整段推理的数值等价证明。

剩余空间用例输入 262140、申请 16 输出，实际返回 4；两个 EOS 强制采样用例各返回 1 token 并按 `stop` 结束。262145-token 输入在入队和前向之前被拒绝。示例 CLI 对 `--prompt-tokens 262144` 在加载模型前报错，退出码为 2。记录的 CUDA 峰值 allocated 约每卡 72.68 GiB，包含启动 profiling 与预分配缓存池；GPU 进程清理后每卡为 4 MiB。

诊断过程有两次脚本问题：首次 8K 诊断在生成后未正确匹配带 UUID 后缀的内部请求 ID，修正后完整重跑 8K 基线通过；256K 驱动在最后的超长输入负例只捕获 `ValueError`，而引擎正确抛出 `VLLMValidationError`，导致原始进程退出码为 1。原始日志、失败状态和 traceback 均保留。随后复核全部 17 个 `VERIFY_PASS`、各 rank 轨迹及预期异常，并通过同一 `TokenizeParams.apply_post_tokenization` 路径的 CPU 边界复核；汇总验收为通过，已完成的 GPU 请求未重跑。

完整配置、源文件指纹、请求 token、分块轨迹、显存、耗时以及上述诊断状态说明保存于[256K 运行报告](../vllm/examples/qwen3.5-loop-mhc/verification_256k.json)。
