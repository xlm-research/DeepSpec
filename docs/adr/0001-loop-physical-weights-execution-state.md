# Loop 模型共享物理层参数，按执行层持有推理状态

该 checkpoint 通过重复执行部分物理层形成更深的前向计算；同一物理层在不同循环轮次收到的序列表示不同。拟采用独立的执行层实例及其推理状态，并让相同物理层对应的执行层共享无状态子模块和参数，以同时保留模型语义、权重共享和 vLLM 现有缓存管理接口。

## Considered Options

- 单个物理层对象循环调用并共享缓存：会把不同轮次的历史混在一起，与当前参考实现不符。
- 单个物理层对象循环调用并手动切换缓存：可表达独立状态，但需要侵入 vLLM 的缓存绑定和执行上下文，增加引擎耦合。
- 每个执行层各自持有完整权重：能隔离状态，但浪费显存，并引入重复加载和参数一致性维护成本。
- 独立执行层共享参数：选用此方案；缓存沿用执行层标识，权重归属沿用物理层标识。

## Consequences

该 checkpoint 的 32 个物理层展开为 80 个执行层，参数装载需要物理层到首次执行位置的映射。Attention/GDN 状态对象不能整体复用；权重加载和后处理完成后仍须验证参数共享，缓存隔离须通过实际读写验证。

用户已将首阶段限定为单机 8 卡、TP=8、PP=1、8K 目标模型推理，并明确不需要对照验证。共享物理参数的规则应用于同一 TP rank 内的多次层执行；TP 算子沿用既有分片，mHC router 在各 rank 完整复制。

此 ADR 的参数与状态归属方案保持不变；它不代表接入已经实现或运行验收通过。具体运行检查和 `grill-with-docs` 问答状态见[实施方案](../qwen3_5_loop_mhc_vllm_plan.md)；术语见[领域词汇表](../../CONTEXT.md)。
