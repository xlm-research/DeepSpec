# Qwen3.5 Loop/mHC：TP=8、128K 单 token TTFT 算子融合优化

状态：根据已完成讨论整理的本地规格；尚未发布到 issue tracker，尚未实施或完成性能验收。测试边界已提出，等待用户核对。记录日期：2026-10-12。

## Problem Statement

用户希望降低 Qwen3.5 Loop/mHC 在本地 vLLM 中独立回答生成的首 token 延迟（TTFT）。主场景是单机八卡、TP=8、128K 上下文总长度、只生成一个 token。此前讨论起于 DSpark 训练供样与三节点示例，但用户已经明确选择独立生成；训练派发等待、训练有效吞吐及 DSpark 推测解码不作为本次优化目标。

现有模型实现已能运行 Loop/mHC，mHC 路由器仍由多个 PyTorch 操作组成。三轮 Loop、每层两次路由，以及每次路由中的 20 轮 log-Sinkhorn 会反复执行小矩阵归一化，构成优先测量的融合候选。历史 Python 栈采样不是 GPU 时间分解，旧功能验收也不是本次可直接使用的性能基线，目前没有证据可以承诺具体加速倍数。

用户不接受量化或其他计算精度改变，也不接受通过减少循环轮次、mHC 流或 Sinkhorn 迭代来提速。优化还必须保留现有特征采集和监督语义，使独立生成的改进能够与既有草稿训练接口共存。

## Solution

围绕目标模型现有生成入口建立可复现的 TTFT 对照，并根据 GPU 分阶段测量实施局部算子融合。优先考察 mHC 投影后的 FP32 log-Sinkhorn，随后依据证据评估 RMS 归一化、四流聚合和残差回写；保留原实现作为参考和回退路径。

主验收请求固定为 131071 个输入 token 加 1 个输出 token，总计 131072，即 128K。独立生成采用 TP=8，不接入 DSpark 草稿推测解码。每组前后对照使用相同硬件、权重、输入和引擎配置，区分冷启动与稳态，报告实际 TTFT、显存及融合收益，不预设加速倍数。

保持 BF16 主干、FP32 mHC router/SSM、原中间转换位置和计算语义。保留三轮 Loop、四条 mHC 流、完整 20 轮 Sinkhorn、128K 能力，以及五份草稿条件特征、独立 post-norm 最终目标状态、已有回答监督和最后一轮回答监督契约。

用户已确认上述目标与约束。此前方案提出的客户端 TTFT 起止、并发一、重复测量次数和零差异启用门槛，属于本规格的具体实施建议；它们不是用户已经逐项确认的额外需求。尤其不能把“精度不要改变”写成用户已经接受某个数值误差阈值，或已经要求所有输入逐位一致。

## Implementation Decisions

1. **已确认的工作范围。** 优化本地 vLLM 的目标模型独立回答生成，采用单机八卡 TP=8；本阶段不包含草稿推测解码。沿用现有单实例 PP=1、DP=1 入口作为实施基线。

2. **已确认的负载。** 上下文上限为 131072，主验收使用 131071 输入和 1 输出。主指标为 TTFT；多 token 连续生成速度不作为主性能验收。

3. **权重与架构边界。** 用户不要求固定最初的 checkpoint。实现读取同结构模型的权重，不依赖具体权重值；同一组基线和候选测量固定权重身份。首轮建议使用现成权重，任意隐藏宽度、层数或新架构的全面泛化不属于已确认范围。

4. **领域与已有架构契约。** 沿用 ADR-0001 的物理层参数共享与执行层状态独立，以及 ADR-0002 的执行层边界特征和独立最终目标状态契约。保持已有 32 个物理层展开到 80 个执行位置的模型语义，不把循环轮次当作生成步。

5. **精度是硬约束。** 保持 BF16 主干、FP32 路由器参数和计算、FP32 SSM 状态，以及系数转回残差或分支类型的既有位置。不引入量化、降低有效计算精度的投影路径、替代近似算法或削减迭代的捷径；也不把原 BF16 中间操作悄悄改为末尾一次转换。

6. **首个融合候选。** 优先评估 mHC 路由器投影后的系数计算和 FP32 log-Sinkhorn。保留每轮先沿最后一维、再沿倒数第二维做归一化，执行完整 20 轮后取指数。初期保留原 FP32 投影，缩小数值对照范围。

7. **后续融合依据。** RMS 归一化、四流聚合与残差回写作为后续候选，是否实现取决于实际热点和数值验收。kernel 技术栈由当前可用工具链与严格语义要求决定，不提前承诺必须使用某一种编译器。

8. **通用 mHC 的复用边界。** 已有通用实现的归一化顺序、普通域 Sinkhorn、epsilon、混合方向和类型转换与本模型不同。可参考其工程组织方式，不能直接作为本模型的等价替换或数值参考。

9. **原实现保留。** 候选通过明确的选择方式与原路径对照；数值条件未满足或形状未覆盖时使用原路径。性能报告必须标明实际执行路径，不能把回退后的运行归入融合收益。

10. **冻结性能对照配置。** 实施建议采用并发一、8192 单步 token 预算、分块 prefill 开启、prefix caching 关闭和 eager 模式。基线与融合版本保持相同配置，首先隔离算子融合的贡献。

11. **请求构造。** 使用固定 token 输入和相同采样条件，建议贪心采样并忽略 EOS，以完成精确的一次输出。记录真实输入、输出计数；输出是特殊 token 时，空文本不等于零输出。

12. **计时边界建议。** 以本机流式 completions 请求为主，从客户端发出请求到收到首个包含生成结果的事件计时。引擎首 token 延迟和 GPU prefill 时间另行报告；不把连接建立、控制事件或纯 GPU 计算时间混充客户端 TTFT。用户已经选择 TTFT，客户端边界是此前完整方案提出的具体口径。

13. **基线先行。** 正式测速关闭 profiler，诊断运行独立进行。固定源码、依赖、权重、输入、精度开关与有效引擎配置，避免使用过时生成版本号单独标识源码。

14. **重复与汇总。** 实施建议在预热后每版本至少完成五次有效测量，报告逐次 TTFT、中位数、范围和加速比；必要时交替测量以检查环境波动。模型加载、初始编译和冷启动单列，不设未经测量的固定倍速承诺。

15. **兼容回归独立运行。** 普通独立生成测速不启用训练特征采集；采集、最终状态和监督 mask 在原有接口上另做回归。保留这项能力不表示每次独立生成都必须负担采集和传输开销。

16. **资源与运行边界。** 在八卡空闲的独占窗口测量，不从 TP=8 的选择推导出停止现有训练的授权。资源尚不可用时可以准备实现和非 GPU 检查，不能将未执行的 GPU 验收标为通过。

17. **交付物。** 交付可回退的局部融合实现、可复现的测速入口、必要正确性回归和性能结果记录。若候选没有可重复的 TTFT 改善，报告结果及原因，不凭单算子微基准宣称达到用户目标。

## Testing Decisions

测试边界方案已经向用户发起核对，当前未收到选择。以下按现有接口组织测试，不引入专用模型服务或为测试新增公共 API。

1. **主测试边界：现有生成入口。** 通过生产使用的 vLLM 生成及流式结果接口观察请求是否完成、token 数是否准确、TTFT 和有效配置是否可复现。测试外部行为，不断言私有函数的调用次数或内部实现布局。

2. **既有先例。** 已有 TP=8 独立生成示例支持精确 token 输入，已有长上下文验收覆盖分块、长度边界和请求复用。复用其请求构造和结果校验方式；原脚本没有正式 TTFT 重复统计，旧诊断脚本与一次性报告不能直接当成本次基线。

3. **必要的数值边界。** TTFT 和生成 token 相同不足以证明计算精度保持。仅对实际替换的融合模块，在相同输入、权重和配置下比较其输出与原实现。测试覆盖常规、接近零、较大有限值，以及完整 chunk 和尾块形状，避免镜像检查实现步骤。

4. **数值验收建议及其状态。** 用户明确禁止精度改变，但没有明确接受数值容差，也没有明确要求逐位一致。此前提出的保守办法是先检查参考路径自身可重复性，再以覆盖用例中替换边界的输出零差异作为候选启用门槛。该门槛仍是方案建议；出现差异时保留原路径并报告，不擅自设定或放宽允许误差，不声称有限测试证明所有输入逐位一致。

5. **数值参考来源。** 使用当前 QwenLoop 的未融合计算作为参考。通用 mHC 测试可复用组织方式，其不同数学定义及宽松容差不能直接沿用。保留 dtype 和转换约束的检查，不能仅凭输出 dtype 判断内部精度。

6. **完整模型对照。** 对固定请求比较最终目标状态与目标 logits，记录生成 token 是否一致。检查有限值和最长请求后的短请求复用；新 kernel 的单元对照不能替代 TP=8 完整请求验证。

7. **采集兼容边界。** 复用已有 Loop 采集契约测试，核对执行层 3、27、51、75、78 的五份特征、顺序与形状，并核对独立 post-norm 最终目标状态。已有假层测试能证明接口契约，不能证明真实 router 的数值正确，因此真实模型数值回归仍需覆盖受影响输出。

8. **缓冲区与监督契约。** 复用现有 direct capture 的缓冲区复用测试与输入、mask 保留测试，防止融合回写覆盖已保存状态、增加内部生成 token 到训练样本或改变最后一轮回答监督范围。

9. **128K 与分块。** 主请求必须实际处理 131071 个输入 token 并返回 1 个输出 token，检查分块状态连续、各执行层历史隔离、请求结束后资源可复用。短请求、chunk 边界和尾块用于正确性回归，不扩展为多档性能交付。

10. **计时完整性。** 使用流式生成结果结束首 token 计时，排除控制事件；同时核对真实输出计数，避免特殊 token 或仅有 usage 信息造成错误测量。单输出不报告有意义的连续 token 平均间隔。

11. **性能与诊断隔离。** GPU trace 用于定位开销，正式 TTFT 来自无 profiler 的运行。保持输入、缓存设置、权重和引擎配置一致，报告重复测量的原始值；显存及启动成本不能因未纳入主指标而省略。

12. **通过条件。** 功能和精度约束满足后，只有可重复的端到端 TTFT 改善才能被称为推理提速。单算子加速、一次更快的请求或历史不同负载的时间不能替代此证据；若无改善，交付记录必须明确说明。

| 验收项 | 可观察的通过证据 |
| --- | --- |
| 主请求 | TP=8 实际完成 131071 输入及 1 输出，长度、停止结果与有效配置可核验 |
| 精度与算法 | 三轮 Loop、四条流、20 轮 Sinkhorn 及现有计算精度、转换语义保持，数值门槛按上述约定执行 |
| 长上下文状态 | 分块历史连续、执行层状态独立，最长请求后短请求仍能完成 |
| 训练兼容 | 五份条件特征、独立最终状态、输入与监督 mask 契约保持 |
| 性能证据 | 同一负载和配置下提供基线、候选的逐次 TTFT、汇总及显存记录 |
| 回退 | 未通过数值或性能条件的候选保留原路径，报告实际执行选择 |

## Out of Scope

- DSpark 草稿推测解码接入、接受率优化和草稿训练效果提升。
- 以三节点供样速度、Mooncake 传输、训练等待或训练吞吐作为本次主优化目标。
- 量化、降低主干或 router/SSM 精度、改变中间转换规则，或以近似计算替换原算法。
- 减少 Loop 轮次、mHC 流、Sinkhorn 迭代，缩短上下文或改变采集监督语义。
- 并发吞吐优化、多 token decode 速度承诺、256K 扩展和多长度性能排行榜。
- 把关闭 eager、整模型 CUDA Graph、改变 chunk 大小或增加硬件列为必交付路线。
- 为所有隐藏宽度、层数、硬件和不同模型架构提供全面泛化。
- 用旧日志或 Python 栈采样推定 GPU 时间占比，或预先承诺固定加速倍数。
- 停止正在运行的训练、修改远程部署、提交代码或发布 PR。
