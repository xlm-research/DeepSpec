# Qwen3.5 Loop + mHC 单机 8 卡推理规格

状态更新（2026-10-10）：8K 已完成功能与结构验收，见[运行报告](../vllm/examples/qwen3.5-loop-mhc/verification.json)。本文件保留 8K 阶段的交付契约；256K 扩展也已完成验收，见[扩展设计与验收记录](qwen3_5_loop_mhc_256k_plan.md)。

## Problem Statement

用户希望使用现有 H800 环境，通过本地 vLLM 推理指定的 Qwen3.5 Loop + mHC checkpoint。接入前，vLLM 尚未注册该 checkpoint 声明的 Qwen3_5LoopForConditionalGeneration 架构，标准 Qwen3.5 实现也没有表达其循环执行和多流残差语义，无法直接加载并按目标模型结构完成推理。

目标权重是训练运行 1009_9b_mhc4_loop3_from50_zxh_glmv25_all16_16nodes 的 ckpt-225-bf16。它包含 32 个物理层，部分物理层重复执行三轮，并在每轮循环区间内使用四条 mHC 流。简单修改架构名称，或把物理层整体重复引用，会遗漏执行层状态隔离、权重装载映射和 mHC 边界处理。

用户已确认首阶段只需要单机 8 卡、TP=8、PP=1、8K 文本推理，不需要与 LightLLM、训练实现或其他运行方式做数值对照，也不需要先接入 TorchSpec 训练或 MTP。

## Solution

在本地 vLLM 中提供原生 Loop + mHC 模型支持，直接读取现有 checkpoint，复用 Qwen3.5 的标准算子、权重分片和推理入口。一个目标模型实例使用八张 H800，配置 TP=8、PP=1、DP=1，支持输入与输出合计最多 8192 tokens。

交付包含模型接入、可复用的启动配置和文本生成验证入口。使用 BF16 主干、FP32 mHC 路由器及 FP32 SSM 状态，以 eager、非分块 prefill 作为首阶段运行基线。完成权重加载、短输入和接近 8K 总长度请求的 prefill、多步 decode，以及请求结束和后续请求运行检查。

验收是功能与结构验收，不设参考输出、数值误差阈值、吞吐或时延指标。运行成功的结论不得表述为已证明与训练实现数学等价。

## User Stories

1. 作为模型使用者，我希望直接加载已提供的 ckpt-225-bf16 权重，以便使用现有训练产物进行推理。
2. 作为模型使用者，我希望保留 checkpoint 原有的架构声明和物理配置，以便避免为适配框架重写模型身份。
3. 作为模型使用者，我希望沿用已有 H800 conda 环境和本地 vLLM 源码，以便在当前工作环境中复现运行。
4. 作为推理部署者，我希望一个模型实例共同使用单机八张 GPU，以便按已确认的 TP=8、PP=1 拓扑运行。
5. 作为推理部署者，我希望数据并行规模保持为一个副本，以便八张 GPU 用于同一个张量并行组。
6. 作为模型使用者，我希望输入与输出总长度支持 8192 tokens，以便处理首阶段要求的 8K 请求。
7. 作为模型使用者，我希望短文本请求能够完成 prefill 和多个 decode 步骤，以便确认完整生成链路可以运行。
8. 作为模型使用者，我希望接近 8K 总长度的请求也能够生成，以便短样例通过不会掩盖长度支持问题。
9. 作为推理部署者，我希望能通过标准文本或 token 输入发起推理，以便同时进行实际文本使用和精确长度检查。
10. 作为模型使用者，我希望实际执行规定的三轮循环，以便加载到的权重按其模型结构参与推理。
11. 作为推理部署者，我希望不同执行层保留各自的序列状态，以便循环轮次之间不会共用同一份推理历史。
12. 作为推理部署者，我希望重复执行的物理层共享参数，以便避免为八十个执行位置重复保存完整权重。
13. 作为模型使用者，我希望每个循环轮次正确展开并收敛 mHC 流，以便四流残差的使用范围符合模型定义。
14. 作为推理部署者，我希望路由器和 SSM 状态保留所需的 FP32 精度，以便整体 BF16 配置不会改变它们的精度要求。
15. 作为推理部署者，我希望 TP=8 下的注意力和 GDN 头数使用正确的分片及复制规则，以便八张卡能够共同完成前向。
16. 作为推理部署者，我希望每张卡持有完整 mHC 路由器和残差流，以便路由计算与已有 TP 算子的输出接口匹配。
17. 作为模型使用者，我希望后段物理层的权重加载到正确的执行位置，以便循环展开不会使不同物理层相互错配。
18. 作为推理部署者，我希望缺失的必要权重在加载时明确报错，以便不会带着未初始化的路由器参数继续推理。
19. 作为模型使用者，我希望文本模式能够合理处理 checkpoint 中的视觉参数，以便首阶段无需初始化视觉推理链路。
20. 作为模型使用者，我希望目标模型推理无需独立 draft 权重，以便 MTP 不成为首阶段启动的依赖。
21. 作为模型使用者，我希望 tokenizer、聊天模板和停止条件得到一致配置，以便文本请求可以正确进入模型并正常结束。
22. 作为模型使用者，我希望不同长度的请求能够分别返回各自结果，以便在同一个引擎中连续使用模型。
23. 作为推理部署者，我希望请求结束后推理资源能够正常复用，以便后续请求不会因状态释放问题失败。
24. 作为推理部署者，我希望不支持的配置明确失败，以便不会把继承来的能力标志误认为已实现的功能。
25. 作为已有 Qwen3.5 使用者，我希望默认模型的构造行为保持稳定，以便新增 Loop 架构不影响原有模型使用。
26. 作为实现维护者，我希望沿用现有模型加载和生成测试入口，以便验证接入行为而无需维护另一套推理框架。
27. 作为模型使用者，我希望验收不依赖运行参考模型，以便工作聚焦于已经确认的八卡推理目标。
28. 作为推理部署者，我希望运行记录说明实际 GPU 拓扑、有效配置和请求完成情况，以便判断是否真正达到了交付条件。
29. 作为模型使用者，我希望本阶段不会扩展为训练、推测解码或长上下文优化项目，以便先完成确定范围内的推理支持。
30. 作为实现维护者，我希望规格区分源码推导和实际运行结果，以便不会把尚未执行的验证当成已通过的证据。

## Implementation Decisions

1. **原生模型接入。** 新增 Loop + mHC 模型模块，注册 Qwen3_5LoopForConditionalGeneration。保留原有 qwen3_5 模型类型，不通过伪装为标准模型或修改原 checkpoint 来绕过架构识别。

2. **最小构造入口。** 在标准 Qwen3.5 的 CausalLM 内层模型构造和 ConditionalGeneration 语言模型构造处提供可覆盖入口，默认目标类保持现状。Loop 子类直接构造目标模型，避免先构造标准层再替换造成重复状态注册。循环执行位于外层实际调用的内层模型前向，不能仅覆盖会被外层绕过的 CausalLM 前向。

3. **物理配置与执行计划分离。** 保留 32 个物理层的配置，另外派生运行时执行计划和层类型。物理层 0 至 3 执行一次，物理层 4 至 27 连续执行三轮，物理层 28 至 31 最后执行一次，共 80 个执行层。不得用原始 32 项层类型直接索引后续执行位置。

4. **参数共享、状态独立。** 遵循 ADR-0001，同一 TP rank 内，相同物理层对应的执行层共享无状态投影、MLP、norm、路由器及 GDN 参数。Attention/GDN 状态对象和缓存身份按执行层独立持有，共需 20 个 full-attention KV 状态位置和 60 个 GDN 状态位置。不能整体共享一个有状态层对象。

5. **构造和加载生命周期。** 尽早建立共享关系，避免先为全部执行层分配完整独立权重。参数加载及其后处理结束后仍须保持共享。执行层标识遵守现有缓存索引规则，只使用一个执行层数字索引，避免把物理层和循环轮次同时编码成多个数字段。

6. **权重映射。** 每个物理层的参数仅装载到其首次执行位置，再由其他对应执行层共享。物理层 0 至 27 的首次执行位置不变；物理层 28 至 31 分别映射到执行层 76 至 79。尤其不得把物理层 28 的权重装入第二轮起点的执行层 28。

7. **复用权重分片规则。** 沿用现有 QKV、GDN 的 QKV/Z 与 B/A 投影、MLP gate/up 等融合加载机制，加载结果使用实际去重参数名。不能把所有 checkpoint 张量机械地八等分，也不能靠忽略未知参数掩盖映射错误。

8. **明确处理非目标权重。** 只有在 Loop gate 关闭时才允许忽略其 logits 参数。视觉参数通过已有文本模式机制处理。路由器 weight 和 bias 都必须完整装载；配置中的 MTP 层数不构成目标 checkpoint 含有可用 draft 权重的证据。

9. **逐轮 mHC 边界。** 每轮进入物理层 4 时，将宽度 4096 的表示复制为四条 mHC 流；该轮离开物理层 27 时，对四条流取均值恢复原宽度。下一轮重新展开，不能把四流残差直接跨轮次保留下去。

10. **mHC 分支顺序。** 每个 mHC 层先完成 attention 路由、流聚合、norm、Attention/GDN 及回写，再完成 FFN 路由、流聚合、norm、MLP 及回写。各分支算子继续处理宽度 4096 的表示，四条流仅存在于残差表示中。prefill 与 decode 使用相同的路由语义。

11. **路由语义。** 展平后的残差先在 FP32 下做不带可学习参数的 RMS 归一化，再执行 FP32 路由器线性计算。前四项经 sigmoid 产生分支输入系数，后四项经二倍 sigmoid 产生回写系数，余下十六项形成四乘四混合矩阵；先沿最后一维、再沿倒数第二维做 logsumexp 归一化，重复二十次后取指数。流混合是混合矩阵左乘残差，不转置矩阵。聚合、回写时按已核实的源码保留系数转换精度和运算顺序。已读实现不消费 pre_scale，因此不额外添加乘 0.5 的操作。

12. **残差与归一化接口。** Loop 内层统一传递完整残差表示，普通层完成 attention 与 MLP 各自的残差相加，mHC 层显式聚合和回写。不能把标准模型延迟相加的残差接口直接连接到四流表示。复用 Qwen3.5 的 Gemma 形式 RMSNorm，其中可学习缩放包含权重加一；它不同于路由器的不带权重 RMS 归一化。

13. **精度。** 主干权重采用 BF16。mHC 路由器的 weight 和 bias 显式保持 FP32，单个路由器形状为 24 乘 16384 和 24；SSM 缓存采用 FP32。全局 BF16 初始化不得覆盖这两项精度要求。

14. **TP=8 数据流。** Full attention 的 16 个 Q heads 每 rank 分配两个；4 个 KV heads 通过现有复制机制使每 rank 持有一个，每个原始 KV head 对应两个 rank。GDN 的 16 个 Q/K heads 和 32 个 V heads 每 rank 分配两个和四个；MLP 中间宽度 12288 每 rank 分配 1536。

15. **mHC 在 TP 下完整复制。** 每个 rank 持有完整四流残差及完整 FP32 路由器。Embedding、Attention/GDN 输出投影和 MLP 输出沿用现有 TP all-reduce，保证路由器看到完整宽度的表示。保留输出归约，不引入改变该边界的 sequence parallel 或 reduce-scatter；不新增 mHC 流间 TP 通信算法。

16. **配置和能力发现。** 新架构接入 Qwen3.5 配置校验，并保留混合模型状态发现以及 GDN 状态形状、精度接口，使当前 V2 runner 正确管理执行层状态。保留所复用外层的模型标记和 processor 机制，但不据此宣称已经支持图像输入。对未实现的并行、量化、LoRA 或推测解码配置明确限制。

17. **部署基线。** 单机八张 H800、TP=8、PP=1、DP=1，最大模型长度和最大批次 token 预算均为 8192。使用现有环境的 V2 runner、safetensors 加载、文本模式和 eager；关闭 prefix caching 与 chunked prefill。单请求 smoke 验证之后再检查少量变长请求，首阶段不承诺吞吐或时延。

18. **长度与停止行为。** 8192 是输入与输出 token 总长度。非分块 prefill 的批次 token 预算至少覆盖该长度。沿用标准 tokenizer、模板和生成配置机制，并明确核对外层 EOS 248046 与文本配置 EOS 248044 的实际生效关系，确保请求按有效停止条件结束。

19. **变更范围。** 核心修改集中在新增模型模块、标准 Qwen3.5 的两处构造入口、模型注册以及配置校验映射。先沿用现有调度器和缓存管理接口；若实际运行暴露接口缺口，应说明原因后做完成本功能所需的修改。

## Testing Decisions

1. **集中在一个已有测试入口。** 主测试边界是 vLLM 对外的模型构造、加载和生成入口，复用现有 LLM 与 VllmRunner 测试工具。通过真实 TP=8 引擎执行下面的场景，不另造 Loop 专用推理框架，也不为了测试公开路由器私有方法。这个具体入口选择需按 to-spec 流程做一次确认；已确认的功能范围和“不做对照”保持不变。

2. **测试行为契约。** 好的测试应验证模型能否加载、请求是否完成、输出是否对应请求、token 总数是否满足限制、停止和资源释放是否正确。不得以具体类内部调用次数、私有属性名称、精确生成文本或固定内存布局作为成功条件。尤其不能仅凭底层 storage 指针相同或不同就判断缓存隔离。

3. **覆盖模块。** 通过统一入口覆盖架构注册及配置识别、模型构造和权重加载、Loop/mHC 前向、TP 算子和混合状态生命周期。参数共享、精度、执行状态类别与必要权重完整性属于加载阶段的校验和诊断；主验收观察完整引擎是否建立并正确处理请求，不为这些私有实现分别设计新的测试接口。

4. **已有先例。** 现有模型生成测试直接通过 LLM 构造和 generate 检查请求返回数量、采样参数及总 token 上限；VllmRunner 已支持 TP、模型长度、eager 和禁用 chunked prefill；现有 prompt validation 测试从同一入口验证非法输入报错。模型注册测试可作为新增架构发现的既有回归依据。只复用这些测试的组织方式，不带入其他模型测试中的参考实现对照、困惑度评估或 MTP 场景。

5. **运行验收场景。** 测试必须使用目标权重及用户确认的八卡拓扑。单卡、缩小的替代模型或只完成初始化都不能替代以下验收：

| 编号 | 场景 | 成功条件 |
| --- | --- | --- |
| AC-01 | 原 checkpoint 加载 | 原架构能够识别，八个 rank 完成初始化和必要权重加载；不存在未解释的缺失参数或重复状态注册 |
| AC-02 | 短输入生成 | 文本或有效 token 输入完成 prefill，并实际触发多个 decode 步骤；返回有效 token 和完成状态，无通信挂起或非法数值错误 |
| AC-03 | 8K 长度支持 | 根据实际 token 数构造接近 8192 总长度的有效请求，预留生成预算；成功完成长 prefill 和多步 decode，无 OOM，总长度不超过 8192 |
| AC-04 | 输入及长度约束 | 非法 token 或超出有效输入长度的请求通过现有校验明确失败；生成预算受总长度约束，不越界执行 |
| AC-05 | 停止行为 | 请求按有效 EOS、停止条件或生成预算正常结束，并报告对应完成状态；长度压力测试与正常停止行为分别覆盖 |
| AC-06 | 变长请求与复用 | 多个不同长度请求分别返回结果；请求结束后后续请求仍可正常生成，没有遗留错误或状态资源耗尽 |
| AC-07 | 支持范围校验 | 明确不支持的配置给出可解释错误，不通过继承来的能力标志静默接受不完整的执行路径 |
| AC-08 | 标准模型回归 | 受构造入口修改影响的既有注册和生成用例通过，标准 Qwen3.5 默认构造目标保持原行为 |

6. **取消数值对照。** 不运行 LightLLM、训练实现、Transformers 或其他配置作为数值参考；不进行整段重算与增量 decode 对照，不比较单卡和八卡输出，不采集参考 hidden states/logits，也不制定 BF16 误差阈值。源码阅读和加载时结构检查不构成参考模型运行。

7. **记录真实证据。** 留存有效配置、八个 rank 的启动情况、请求实际输入与输出 token 数、完成状态及异常信息。状态生命周期检查与权重诊断只证明各自检查到的运行契约，不扩大解释为完整数值等价性证明。当前规格整理阶段不启动模型或执行上述测试，结果由后续实现阶段填写。

## Out of Scope

- 与参考推理框架、原训练实现、整段重算或其他 GPU 拓扑的数值对照，以及困惑度、模型质量或误差阈值评估。
- TorchSpec 隐状态采集、数据传输、草稿模型训练及训练链路接入。
- MTP、EAGLE 或其他推测解码，以及独立 draft 的接入。
- 图像、视频及其他多模态输入。
- 256K 长上下文；首阶段之外的模型长度保证。
- PP 大于一、多机、多个 DP 副本，以及其他并行拓扑的正式支持承诺。
- 量化、LoRA、prefix caching、chunked prefill、编译、CUDA Graph 和 sequence parallel 优化。
- 吞吐、时延和显存压缩优化指标，以及新增定制 HTTP 服务协议或独立调度系统。
- 为兼容性重写原 checkpoint、原地改变其权重精度，或将八十个执行位置导出成八十套独立权重。

## Further Notes
